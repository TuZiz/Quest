# 中央仓库提取进度修复

适用：Quest 1.0.0 + PlayerVault 1.0.0，Purpur 26.3 / Java 25；编译 API 为 Paper 26.2.build.126-stable。

## 原因

「资源的归宿」仍使用 `genlite.extract`，但物流核心和 `/genlite warehouse` 已打开 PlayerVault 的队伍中央仓库。旧版只有 Genlite 自己的提取菜单递增该计数，PlayerVault 成功取货不会通知 Quest，因此任务会停在 0/8。

## 修复范围

- PlayerVault 提供 `withdrawnToInventory(WarehouseTarget)` 只读 API，从持久化的唯一背包事务审计构建每个仓库的累计成功提取量。查询无文件 IO，后台保存成功后才发布，不改变库存或账本格式。
- Quest 通过可选 API 连接指定空岛的队伍仓库，沿用现有每秒发现/恢复流程。个人仓库和其他空岛不混计。
- Quest 在原有 SQLite `facts` 表保存每个空岛的首次接入基线及最后观察值。更新前历史不追溯发奖，已有目标基线、进度、完成记录、领奖和邮箱记录不删除、不重置；以后解锁的任务继续从解锁时的真实总量开始。
- 无成功确认的操作、取消、背包已满、存入和直接 API 扣库存不计数。已成功确认的体验即使后来因玩家存档回退撤销库存效果，也不撤销体验计数或重放物品。
- 重启后由持久化审计和 Quest 基线恢复，重复读取不重复累加。源计数回退时报告错误并冻结对应推进，不猜测补发。
- 本次没有更改任务数量、奖励、GUI、HUD、贴图或线上玩家文件；无需改任务 YAML。

## 更新

必须配套更新 `Quest-1.0.0.jar` 和 `PlayerVault-1.0.0.jar`。Genlite 不需要本次修补。

按 leaf 的统一交付脚本分别 SSH 上传到 `D:\Purpur-server\plugins\update\`，由脚本备份旧 JAR并校验 SHA256。没有自动重启或热加载。完整部署回执另存于本次 `target/warehouse-progress-delivery/`。

正常重启后，应看到 Quest 日志：

```text
PlayerVault committed team warehouse withdrawal progress connected; historical totals use per-island baselines
```

等插件就绪后，从物流核心打开**队伍中央仓库**，再成功取出 8 个资源到背包即可验证本任务。可以分次提取、同岛成员共同推进；个人仓库提取不计。更新前漏记的提取无法可靠判定是否发生在任务解锁后，因此不自动补算。

恢复版本时不要单独恢复某个插件的玩家存档。JAR备份仅供回退程序；本次不修改数据库 schema，也不覆盖玩家数据库或仓库文件。
